# 后端存储与协作架构说明

本文说明当前后端存储实现、Agent 状态持久化方式、部署边界和团队协作规范。早期 JsonStore 方案已经退出主运行链路，当前事实以 SQLite + Prisma 为准。

## 1. 当前存储结论

系统使用 SQLite 保存业务数据，Prisma 负责数据访问。数据库默认位于持久化数据目录，容器环境通常映射为 `/app/data`。

选择 SQLite 的原因不是“它等同于 MySQL”，而是当前系统满足以下条件：

- 单个后端实例写入。
- 20～30 人左右的内网团队规模。
- 消息、任务、站会和 Agent 执行量可控。
- 希望保持单文件备份和低运维成本。

SQLite 提供事务和索引，解决了 JsonStore 的并发覆盖、全目录扫描和文件损坏风险。它仍然是单机数据库，不适合多个后端副本同时写同一个数据库文件。

## 2. 数据分层

### 2.1 业务数据

- 消息与上下文：保存飞书消息、引用关系和交互上下文。
- 任务与更新：保存 Task、TaskUpdate、TAPD 映射和状态变更轨迹。
- 站会：保存成员提交、未提交记录和汇总。
- 日报与看板：保存生成结果和历史访问数据。
- 会议纪要：保存归档文件记录和分发状态。
- 配置与日志：保存动态配置、群组成员、审计和幂等信息。

### 2.2 Agent 数据

Agent 化升级新增以下持久化对象：

- Agent Catalog：外部 Agent 的 Manifest、Installation 和 Binding。
- Trigger Claim：触发事件的幂等抢占结果。
- Agent Run：一次执行的状态和关联信息。
- Agent Step：执行步骤、开始结束时间和错误。
- Artifact：Agent 生成的结构化产物。
- Delivery Outbox：产物的投递状态、重试次数、租约和错误。

当前这些对象通过统一的持久化 KV 接口复用 Idempotency 表。这样可以在不立即扩表的情况下完成重启恢复和 CAS，但它是过渡实现。

## 3. 一致性设计

### 3.1 任务更新

任务状态和更新记录先持久化，再触发通知。通知失败不会造成“用户收到成功但数据库没有记录”的矛盾。

### 3.2 定时任务

调度任务使用原子 Claim。多个 Tick 或重复事件竞争同一个业务键时，只有一个执行者获得处理权。

### 3.3 Agent 触发

Trigger 使用 `workspaceId + botInstanceId + triggerId` 形成作用域内的防重边界。重复调用返回已有 Run，不重复产生 Artifact 和 Delivery。

### 3.4 消息投递

Artifact 先写入 Outbox。Worker 领取有期限的租约后发送；进程中断导致租约过期时，后续 Worker 可以重新领取。可重试错误进入下一次重试，不可重试错误或耗尽次数后进入终态。

## 4. SQLite 的使用边界

适合：

- 单机或单后端 Pod。
- 中小团队 ChatOps。
- 需要简单备份和恢复。
- 查询与写入量未达到持续高并发。

不适合：

- 多个后端副本同时写一个 PVC 上的数据库文件。
- 需要跨地域高可用。
- Agent Run、Artifact 和日志进入百万级后仍要求复杂实时分析。
- 需要独立数据库权限、审计和读写分离。

达到这些条件时，应评估 PostgreSQL。迁移不只是修改 Prisma Provider，还要检查字段类型、默认值、索引、事务语义、连接池、迁移脚本和回滚方案。

## 5. 当前 Schema 管理方式

仓库当前提交 `backend/prisma/schema.prisma`，启动和 `setup` 脚本使用 `prisma db push` 同步结构，尚未建立正式的 Prisma Migration 历史。

因此：

1. 开发环境可以使用 `bun run db:push` 建立本地结构。
2. 生产环境变更 Schema 前必须备份数据库，并在生产副本上验证 `db push` 结果。
3. 删除字段、修改类型或增加非空字段属于高风险操作，不能直接随镜像启动自动执行。
4. 在下一次重要 Schema 变更前，应建立 Migration Baseline，把结构演进改为可审查、可回滚的迁移文件。

旧文档中“仓库已经提交 migrations，严禁 db push”的描述与当前代码不一致，现已更正。

## 6. 环境隔离

团队只共享代码和 Schema，不共享业务数据库。

- 每名开发者使用独立的本地 SQLite 数据库。
- 每名开发者使用独立的飞书测试机器人和测试群。
- TAPD 联调使用测试 Workspace，禁止在本地直连生产项目修改真实工单。
- 外部 Agent 使用测试 Endpoint 和测试 Secret 引用。
- 生产 `data.db` 不复制到个人电脑；排障优先使用脱敏副本。

## 7. 备份与恢复

### 7.1 备份

- Kubernetes 必须为 `/app/data` 挂载持久卷。
- 每日至少生成一次数据库一致性快照，并复制到独立存储。
- Schema 变更、批量同步和版本发布前额外备份。
- 备份应包含动态配置目录，但不应把明文 Secret 放入普通归档。

直接复制正在写入的 SQLite 文件可能得到不一致快照。优先使用 SQLite 在线备份能力，或在短暂停写窗口中复制数据库及其 WAL 相关文件。

### 7.2 恢复演练

至少按季度验证：

1. 在隔离环境恢复数据库。
2. 执行 Prisma Client 初始化和健康检查。
3. 验证任务、站会、Agent Catalog 和未完成 Outbox 记录。
4. 启动 Worker，确认过期租约可以恢复且不会重复投递已完成记录。

## 8. Agent 数据演进建议

当 Agent 数量、运行历史或投递量明显增长时，按以下顺序拆表：

1. `AgentRun` 与 `AgentStep`：支持按状态、Agent、时间和 Bot 查询。
2. `Artifact`：保存类型、校验和、对象存储引用和保留时间。
3. `DeliveryOutbox`：为状态、租约到期时间和下次重试时间建立组合索引。
4. `AgentInstallation` 与 `BotAgentBinding`：支持禁用、版本升级和多机器人配置。
5. `TriggerClaim`：建立过期和归档策略，避免幂等表无限增长。

拆表时必须保持现有接口不变，先迁移数据并做双读校验，再切换实现。

## 9. 协作要求

- 修改任务相关存储时，通过 TaskService 收敛业务规则。
- 修改站会相关存储时，通过 StandupService 统一口径。
- 修改 Agent 持久化时，同时测试重复 Trigger、状态迁移、重启恢复和租约回收。
- 任何 Schema 变更都要附迁移/回滚说明和备份验证结果。
- 数据修复脚本必须可审计、可重复运行，并先在脱敏副本验证。
